# План адаптации turbine-python-sdk

Дата: 2026-11-05. Статус: реализован; локальная приёмка завершена.
Результаты приёмки: [compatibility.md](compatibility.md).

Проверенная исходная точка: `fadbf4c2140bc6eecd54ac2acfde6ff6195af154`
репозитория `SystasisIO/turbine-python-sdk`. При начале реализации повторно
проверить HEAD и изменения upstream; не переносить этот план на другую версию
без проверки затронутых контрактов.

## Цель и границы

Подготовить самостоятельный Python SDK, который можно установить и использовать
для интеграции с TurbineOS на следующей итерации. Сохранить выполнение workflow
через Comfy API v2 и добавить согласованные каталог нод и оценку стоимости.

Этот план изменяет **только SDK**. В него не входят изменения turbine-backend,
его зависимостей, схем, модулей, конфигурации или документации. Реализация
серверного Comfy API v2 принадлежит команде TurbineOS. Ни backend, ни сервер
не используются как среда для разработки или обязательная зависимость SDK.

SDK не принимает финансовых решений: не резервирует кредиты, не рассчитывает
наценку, не создаёт локальный Job и не ведёт транзакции или outbox. Каталог
пакетов, финансовый допуск, детализация фактических списаний и возвраты требуют
отдельных принятых серверных контрактов и не добавляются попутно.

Документ первоначально подготовлен без реализации. Работы ниже описывают
принятый объём SDK; фактические результаты фиксируются в отчёте совместимости.

## Согласованная основа

| Область | Целевое решение |
| --- | --- |
| Репозиторий | `turbine-python-sdk` |
| Дистрибутив | `turbine-sdk` |
| Python-пакеты | `turbine_sdk`, `turbine_low` |
| Основные клиенты | `Turbine`, `AsyncTurbine` |
| Python | Не ниже 3.11; проверяемые версии 3.11, 3.12 и 3.13 |
| HTTP | `httpx2`, с необязательной передачей готового sync/async клиента |
| Выполнение | Существующие workflows, jobs, assets, outputs, отмена, ожидание и SSE |
| Расширения | `client.turbine.nodes.list()`, `client.turbine.nodes.get(class_type)`, `client.turbine.estimate_prompt(...)` |
| Общие типы | Сетевые модели v2 и однократно определённые схемы каталога и оценки |

Comfy Router сохраняется как отдельная возможность исходного SDK. Его каталог
моделей не заменяет `/object_info`, каталог пакетов TurbineOS или финансовую
детализацию. Нативные HTTP-ответы и WebSocket-события Comfy frontend не становятся
вторым интерфейсом выполнения внутри SDK.

## Что уже есть и что действительно требуется изменить

В исходнике есть low transport с поддержкой передачи готового клиента и
разделением владения соединениями. Public-клиенты этой настройки ещё не имеют.
Выполнение workflow, загрузка assets, SSE, обработка очереди и Router уже
реализованы; писать их заново не требуется.

Обнаруженные особенности, которые должны попасть в приёмку:

- Public-клиенты берут адреса из `COMFY_*` и по умолчанию используют Comfy Cloud.
  Один bearer token отправляется на оба настроенных origin: workflow и Router.
  Это предположение нельзя автоматически перенести на TurbineOS.
- `assets.from_url()` делает отдельные HTTP-запросы вне основного клиента.
  Простое добавление параметра в конструктор не охватит эти загрузки.
- Подготовка workflow заменяет Asset handles ссылками `core/ASSET` при отправке.
  Оценка исходного `Workflow.json` не гарантирует оценку отправляемого графа.
- Основные модели генерируются из vendored OpenAPI. Router и часть методов,
  например metadata/list_jobs, имеют дополнительные handwritten контракты.
- В fork остались upstream-настройки владельцев, организационных workflows и
  публикации. Release workflow активен; комментарий о его отключении устарел.

Этот документ заменяет прежний проект плана в части имени поставки, Python floor,
HTTP-библиотеки и состава текущей SDK-итерации. Старые документы других
репозиториев в рамках этой задачи не изменяются.

## Этап 1. Закрепить контракты и конфигурацию

Составить в SDK короткую таблицу совместимости: метод, wire-контракт, источник,
sync/async реализация, локальная проверка и результат живой проверки. Разделить
исходный v2, Router и три согласованных расширения. Наличие метода в клиенте
не считать доказательством его реализации в TurbineOS.

Целевой контракт конфигурации для реализации:

- `base_url` задаётся в конструкторе; если отсутствует, читается
  `TURBINE_BASE_URL`. Отсутствие адреса — локальная ошибка, без перехода в Cloud
  и без придумывания публичного адреса TurbineOS. Пустой или неверный явный URL
  отклоняется, а не заменяется значением из окружения; пустой env тоже ошибка.
- Пропущенный `api_key` означает чтение `TURBINE_API_KEY`; явный `api_key=None`
  запрещает добавление SDK bearer. Различить их внутренним sentinel, без
  новой публичной абстракции. Пустой/пробельный env означает отсутствие ключа,
  а явно переданная пустая/пробельная строка отклоняется как ошибка настройки.
  Приоритет явного аргумента над окружением проверяется.
- `router_base_url=None` отключает Router; включение — только явным аргументом.
  Запросы к отключённому Router завершаются локальной понятной ошибкой.
  Унаследованный адрес `api.comfy.org` не активируется автоматически.
  Это состояние передаётся до low transport; namespace `client.models`
  сохраняется. Скрытого fallback на Router env нет, fixtures включают Router явно.
- Явно включённый Router использует ключ данного экземпляра; вызывающая сторона
  отвечает за выбор подходящего адреса и ключа. Работа с двумя разными ключами
  в одном экземпляре не добавляется без отдельного требования.
- `COMFY_*` не читаются скрыто. Не использовать глобальное изменение окружения,
  `sys.modules` или `httpx2.alias_httpx()` для совместимости библиотек.
- Для подключения используется параметр `client` с типом
  `httpx2.Client | None` либо `httpx2.AsyncClient | None`; он передаётся в уже
  существующий low transport. Новый универсальный транспортный интерфейс не нужен.

Сохранить upstream Router wire-константы и их проверки независимо от того,
включён ли Router в конкретном экземпляре. Изменение default-поведения Turbine
не является изменением канонического серверного контракта Comfy.

Результат этапа: явный контракт конструкторов, адресов, владения клиентом и
источников схем. Никакие новые бизнес-поля или методы сервера из него не следуют.

## Этап 2. Переименовать поставку и обновить зависимости

Перенести `src/comfy_sdk` в `src/turbine_sdk`, `src/comfy_low` в
`src/turbine_low`. Переименовать основные клиенты, low-клиенты в
`TurbineLow`/`AsyncTurbineLow`, базовое исключение SDK в `TurbineError`.
Сохранить назначение остальных существующих исключений и ресурсов.

Обновить согласованно:

- `pyproject.toml`, `uv.lock`, metadata, ссылки проекта, пути wheel/sdist,
  оба `py.typed`, определение `__version__` и User-Agent по metadata
  установленного `turbine-sdk`;
- imports, annotations, exports, fixtures, примеры и проверку sync/async parity;
- Python floor, classifiers, Ruff, mypy, codegen target и CI matrix;
- пути генерации, drift-проверок, coverage и исключений generated-файлов;
- действующие README, CONTRIBUTING, AGENTS и другие инструкции о запуске
  проверок, сохранив требования к генерации и типизации.

Не делать глобальный replace слова Comfy. Сохранить MIT notice, происхождение
кода, upstream-ссылки как источники, историю изменений, wire headers и поля,
например `extra_data.api_key_comfy_org`. Старые alias-пакеты и обёртки клиентов
в новой поставке не нужны. Совместимость здесь означает сохранение поведения
протокола и сценариев при переходе на новые imports.

Перевести собственный HTTP-код SDK на `httpx2`: transport, assets, retries,
исключения, jobs/SSE и Router resources. Заменить соответствующие типы и
перехваты исключений; наличие похожего API не означает взаимозаменяемости
объектов `httpx` и `httpx2`.
[Правила миграции HTTPX2](https://pydantic.dev/docs/httpx2/get-started/migration/).

Сохранить политику «предупреждения об устаревшем API — ошибки»: добавить
pytest-фильтр для `HTTPXDeprecationWarning`, который наследует `UserWarning`
и не покрывается существующим фильтром `DeprecationWarning`. Точное имя
импорта проверить на выбранной версии HTTPX2.

Выбрать и закрепить проверенный диапазон HTTPX2 на момент реализации,
проверить минимальную разрешённую версию. Не удалять `blake3`, Pydantic или
другую используемую зависимость ради сокращения списка. Отсутствие `httpx`
требуется в собственных runtime imports и прямых runtime dependencies SDK;
наличие пакета у инструментов разработки оценивается отдельно.

Результат этапа: воспроизводимая установка под новым именем с сохранённым
поведением существующего SDK и без второго собственного HTTP-стека.
До первого PR или release проверить унаследованные организационные workflows
и отключить чужие внешние интеграции; порядок выпуска описан в этапе 6.

## Этап 3. Завершить настройку и жизненный цикл транспорта

Без передачи клиента SDK создаёт и закрывает его. Переданный клиент остаётся
собственностью вызывающей стороны: `close/aclose` и выход из контекста SDK
его не закрывают. SDK не меняет общие headers, auth, timeout и redirect settings
переданного экземпляра.

Обычные запросы используют настройки переданного клиента; собственный клиент
сохраняет исходный общий timeout 30 секунд. Существующие специальные timeout
для SSE и Router остаются явными параметрами соответствующих запросов.
Закрытие response streams обязательно при успехе, ошибке и отмене coroutine.

Все HTTP-запросы, включая `assets.from_url`, проходят через соответствующий
sync/async клиент. При этом SDK credentials нельзя передавать произвольному
URL загрузки. Проверить отдельно defaults `Authorization` и auth переданного
клиента: отсутствие добавленного SDK header ещё не означает отсутствие
унаследованного header. Для внешних загрузок подавлять не предназначенную им
авторизацию на уровне запроса, не меняя клиент целиком.

Сохранить работоспособность signed downloads и redirects с обычным переданным
клиентом, у которого redirects выключены. Это исключение из наследования
defaults: content download и `assets.from_url` задают redirects на запросе,
получение signed URL сохраняет запрет redirects. Явный SDK key не должен
подменяться default auth переданного клиента. Область действия credentials,
переход на другой origin и настройки TLS проверяются отдельно. Учесть отличие
HTTPX2 в работе с системным хранилищем сертификатов; не отключать проверку TLS.

Существующий SSE decoder, retries и multipart переиспользуются. Наличие этих
возможностей в новой библиотеке не является основанием переписывать их.
Не добавлять автоматический повтор submit с новым идентификатором после
неопределённого сетевого результата. Сохранять исходный идентификатор и
контекст ошибки; серверное восстановление принятого задания требует своего
контракта. Повтор `idempotency_key` в v2 нельзя считать возвратом старого ответа.

Результат этапа: public injection работает для всего SDK, не меняя владение
ресурсами и правила безопасной передачи ключей.

## Этап 4. Добавить общие схемы и ресурсы расширений

| Public-метод, sync и async | HTTP | Результат |
| --- | --- | --- |
| `client.turbine.nodes.list()` | `GET /api/object_info` | Каталог определений нод |
| `client.turbine.nodes.get(class_type)` | `GET /api/object_info/{class_type}` | Ответ конкретного маршрута: отображение имени ноды в её определение |
| `client.turbine.estimate_prompt(prompt)` | `POST /api/prompt/estimate` | `EstimateReply` |

Маршруты расширений используют тот же transport, ключ и origin, что v2.
Проверить deployment prefix, разрешение ссылок и percent-encoding имени ноды.
Не получать `/api/v2/object_info` или двойной `/api/api` из автоматического
добавления v2 prefix. Native-маршруты не добавляются в точный набор
`OPERATION_IDS` upstream; для расширений нужна отдельная проверка покрытия.

Тело оценки — только `{"prompt": ...}`. Метод принимает подготовленный
JSON-граф `PromptGraph`, без Asset handles. Неподготовленные объекты отклоняются
до HTTP-запроса. Оценка не загружает файлы, не создаёт Job и не запускает workflow.
Подготовка assets для `submit/run` сохраняется как раньше; автоматическое
`estimate(workflow)` с материализацией не входит в этот этап.

Это ограничение явно отражается в примерах: для сопоставимого preview и запуска
нужно передать один и тот же подготовленный граф. Локальный сервер проверяет
равенство записанных графов; эквивалентность native file references и v2
`core/ASSET` подтверждается командой TurbineOS на живом сервере. SDK её не
имитирует собственной конвертацией.

Единственные общие денежные схемы:

| Схема | Поля |
| --- | --- |
| `Money` | `amount`: строка неотрицательного целого; `precision`: целое ≥ 0; `unit`: непустая строка |
| `NodeEstimate` | `node_id`: непустая строка; `model_id`: непустая строка или null; `price`: `Money` |
| `EstimateRequest` | `prompt`: `PromptGraph` |
| `EstimateReply` | `total`: `Money` или null; `nodes`: список `NodeEstimate`; `breakdown_complete`: bool |

Все перечисленные поля обязательны. Nullable-поля также должны присутствовать,
но допускают null в качестве значения. `amount` сериализуется строкой ASCII-цифр,
без float; `precision` не принимает boolean. Неизвестная цена не превращается
в ноль. Допустимы `total=null` и известная часть `nodes` одновременно.
Не придумывать правило, по которому `breakdown_complete` означает успешный
запуск или окончательность тарифа. Не добавлять quote ID, TTL, revision,
financial acceptance, лимит списания и новые валютные enum.

Схемы каталога сохраняют исходные descriptors входов, enum-списки, порядок,
дополнительные метаданные нод и различие отсутствующего поля от null.
Схемы графа сохраняют связи между нодами и `_meta`. Не писать отдельный DTO
для каждого class_type и не переписывать содержимое пакетов вручную.

Размещение внутри существующих слоёв:

- `turbine_low/models/`: generated v2 остаётся generated; новые общие типы
  определяются один раз в небольших модулях `catalog`, `graph`, `pricing`.
- `turbine_sdk/schemas/`: только явные переэкспорты общих Pydantic-типов,
  пригодные для импорта без создания SDK-клиента; новых копий моделей здесь нет.
- Public-ресурсы расширения располагаются рядом с существующими ресурсами
  `turbine_sdk`, low HTTP-методы — в существующем transport. Не переносить
  backend-архитектуру modules/services/repository в клиентскую библиотеку.

Upstream OpenAPI и `_generated.py` нельзя править вручную ради расширений.
Для небольшого нового набора достаточно типизированных Pydantic-моделей,
принятых JSON fixtures и проверки их схем; второй генераторный фреймворк
не нужен. Когда сервер предоставит канонический контракт расширений,
проверить соответствие и отдельно решить генерацию из этого источника.
Не склеивать OpenAPI 3.0 и 3.1 без преобразования диалектов и проверки `$ref`.

Переиспользовать согласованные формы, а не копировать donor-код буквально:
Python 3.12 `type` aliases и `pydantic.MISSING` нельзя перенести в библиотеку
с Python 3.11 и `pydantic>=2.6` без проверки. Использовать поддерживаемые
средства Pydantic для omitted fields; нижнюю границу зависимости подтверждать
тестами, меняя её только при конкретной необходимости.

Ошибки новых native-маршрутов декодируются по их реальному формату, а не по
предположению о v2 envelope. Сохранять status, безопасный код и полезные
подробности в существующей иерархии SDK; не создавать FastAPI HTTPException.
Неизвестное тело, malformed JSON и ошибка валидации ответа должны давать
различимую ошибку клиента без ключей и секретных заголовков.

Результат этапа: три работающих расширения и стабильный импорт общих типов.

## Этап 5. Проверить SDK как независимую поставку

Расширять существующий stdlib HTTP stub и `server.state`. Не подключать backend,
не добавлять FastAPI как тестовую зависимость и не подменять HTTPX mocks.

Обязательная приёмка будущей реализации:

1. Полный существующий offline-набор: workflow, assets/dedup/multipart, outputs,
   jobs/list/metadata, отмена, ошибки, retries и Router. Sync/async parity сохранена.
2. Новые маршруты: точные URL, заголовки и body; каталог, unknown/partial/complete
   estimate; ошибки 4xx/429/503, неверный JSON/schema и timeout. При оценке
   в журнале HTTP нет запросов создания Job или запуска workflow.
3. Валидация Money, roundtrip графа/каталога, omitted/null, композиция собственных
   Pydantic envelopes с импортированными SDK-типами. Публичный schema import
   не читает конфигурацию backend и не выполняет сетевых запросов.
4. Owned/borrowed lifecycle, закрытие потоков, отмена coroutine, signed downloads,
   redirects и auth isolation, два независимых клиента с разными настройками.
5. SSE reconnect сохраняет исходную семантику: без обещания replay, которого нет
   в серверном контракте; итоговый GET Job остаётся источником состояния.
6. Ruff lint/format, `mypy src`, полный pytest на 3.11/3.12/3.13;
   codegen drift, Router error/meaning и route/host/media drift; public hygiene.
   Pin генератора не обновлять попутно. Новые public-функции полностью типизированы.
7. Wheel и sdist, `twine check`; установка из wheel вне checkout без editable
   install и PYTHONPATH. Проверить exports, `py.typed`, metadata, version/User-Agent,
   повторяемую сборку из sdist и возможность соседства с upstream `comfy-sdk`.
8. Минимальный consumer в тестах/примерах SDK: импорт общих схем, синхронный
   и асинхронный клиент, nodes → подготовленный graph → estimate → submit →
   wait/events → outputs. Исполнение проходит через локальный stub; consumer
   не импортирует backend и не пишет собственный HTTP-клиент.
9. Проверка минимальных разрешённых runtime-зависимостей; отчёт о dependency
   tree свежей установки. Наличие `httpx` в dev-инструментах не маскировать как
   runtime-зависимость SDK и не удалять чужие транзитивные зависимости силой.

## Этап 6. Подготовить передачу на интеграцию

В SDK обновить краткую инструкцию установки и перехода с upstream imports,
примеры public client injection, общих схем и трёх расширений. Зафиксировать
проверенный commit, версию Python/зависимостей, результаты проверок и ограничения
сервера. Для следующей итерации достаточно устанавливаемого wheel/sdist или
точно закреплённого commit; публикация на PyPI не является предварительным
условием интеграции.

Граница типов для потребителя:

| Типы SDK | Что получает потребитель |
| --- | --- |
| Сетевые Job/Asset, ответы и события v2 | Существующие SDK-типы, без собственных сетевых DTO |
| Каталог нод, PromptGraph, Money и EstimateReply | Общие Pydantic-типы, пригодные для композиции |
| Native frontend HTTP/WS envelopes | Не поставляются вместо собственных протокольных ответов приложения |

Клиентская библиотека не должна требовать параллельного HTTP-транспорта для
перечисленных поддержанных операций. Это не обещание покрытия всех маршрутов
Comfy frontend или всех ещё не принятых финансовых API.

При будущей реализации отключить унаследованные организационные workflows,
обращающиеся к чужим CLA/review integrations. Настройки CODEOWNERS и выпуска
заменять только на реальные согласованные права владельца fork. Сохранить
общие CI, build, drift и hygiene gates. Не публиковать `turbine-sdk` автоматически
через унаследованный release workflow до настройки собственного назначения
и отдельного разрешения на выпуск. MIT notice остаётся в поставке.

## Условия завершения и внешние зависимости

**SDK готов к интеграции**, если выполнены этапы 1–6, есть устанавливаемый
артефакт, независимый consumer, полный отчёт проверок и закрытые замечания
ревью. Это проверяется без изменения backend.

**Живая совместимость с TurbineOS** подтверждается отдельно: доступный сервер
должен выполнять v2 jobs/assets/SSE, каталог и estimate. Реальные тесты запускаются
только на предоставленном тестовом окружении с разрешёнными ресурсами.
Пропуск env-gated integration test отмечается `NOT_RUN`, а не успешной проверкой.

До реального платного выполнения остаются внешние условия, которые SDK не решает:

- Реализация и подтверждение сервером v2 методов, metadata/list_jobs и форматов
  ошибок; подтверждение формата ответов трёх расширений.
- Поиск уже принятого задания после потери ответа submit. Отдельный механизм
  должен быть согласован серверной командой; локальный stub его не доказывает.
- Эквивалентность оценки подготовленного графа и исполнения с файловыми входами.
- Финансовый допуск, лимит расхода, окончательные начисления и возвраты.
- Преобразование v2 состояния/результатов в native Comfy HTTP/WS, включая binary
  previews: это последующая задача приложения, не новый SDK-клиент в обход v2.

Рекомендуемый порядок работ: этапы 1–3 → этап 4 → полная приёмка этапа 5 →
ревью и документация этапа 6. Проверки этапа 5 добавляются вместе с изменениями,
а не откладываются до конца. После этого отдельная команда запускает интеграцию
в backend; данный план не включает её реализацию.
